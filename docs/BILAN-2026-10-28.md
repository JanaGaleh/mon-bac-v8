## Livraison

Interface responsive avec navigation mobile, accueil élève, cours et recherche, quiz/corrections via RPC, résultats, profil, codes enseignant et déclaration de règlement. Espaces enseignant et administrateur reliés aux tables et RPC existantes. Cache limité aux fichiers de l’interface ; aucune donnée utilisateur Supabase dans Cache Storage. Contenus pédagogiques rendus comme texte pour éviter les injections HTML. CSP sans scripts inline ni CDN ; dépendance Supabase locale et versionnée.

Aucune migration, aucune politique, aucun droit ni aucune fonction SQL modifiés. Aucune donnée préexistante supprimée. Les actions d’écriture sont déclenchées uniquement par les formulaires des utilisateurs autorisés.

## Fonctionnalités restantes et décisions nécessaires

1. **Catalogue de quiz élève** : aucune politique SELECT élève sur `quiz`. L’ouverture par numéro fonctionne via `demarrer_quiz`. Un catalogue nécessite une RPC dédiée aux métadonnées autorisées ou une politique soigneusement limitée. Validation préalable obligatoire.
2. **PDF, documents et vidéos** : `ressources` n’est lisible que par l’enseignant propriétaire, sans politique d’écriture. Prévoir stockage privé et liens signés après vérification d’accès, puis validation des permissions. Aucun contournement côté navigateur.
3. **Catalogue Premium avant achat et tarifs lisibles** : les cours Premium non autorisés sont entièrement masqués par RLS, les tarifs sont lisibles uniquement par leur enseignant. Le formulaire utilise donc le montant communiqué par l’enseignant, vérifié par la RPC. Pour une boutique, exposer uniquement des métadonnées sans contenu protégé, après validation.
4. **Publication pédagogique** : ajouter de vrais cours gratuits et compléter les contenus/corrigés existants. Aucun cours fictif publié durablement.
5. **Édition avancée des quiz** : l’interface ajoute des questions/corrigés, mais n’offre pas encore l’édition des questions existantes, les variantes de réponses texte, le brouillon/publication, ni l’historisation du corrigé. Les questions et choix sont créés en deux requêtes : la reprise vérifie les choix déjà enregistrés pour limiter les doublons. Une RPC atomique et une gestion de brouillon seraient préférables, à concevoir et faire valider.
6. **Administration avancée** : création/invitation d’utilisateurs, changements de rôles, tarifs et commissions ne sont pas implémentés ; ils nécessitent un traitement serveur et un modèle d’autorisation validé.
7. **Échelle et progression** : lectures limitées à 500 lignes ; pagination serveur, historique détaillé, suivi de lecture, objectifs, notifications et paiement automatisé restent à développer.
8. **Sécurité à arbitrer** : protection contre les mots de passe compromis désactivée ; extension `btree_gist` dans le schéma public. Les quatre tables sans politiques (`administrateurs`, `commissions`, `journal_admin`, `reponses_quiz`) sont actuellement verrouillées pour les accès directs concernés et peuvent être utilisées par RPC. Ne pas ajouter de politiques permissives pour faire disparaître ces alertes.
9. **Cohérence des administrateurs** : certaines RPC utilisent `profils.role`, d’autres `administrateurs`. Le compte actuel fonctionne ; tout nouvel administrateur doit être provisionné selon les deux contrôles existants, sans modification depuis le navigateur.
10. **Année scolaire** : `decider_paiement` cible actuellement `2026-2027` dans le code serveur existant. Prévoir une évolution validée avant le changement d’année.
11. **Tests appareils** : Android/Chrome, iPhone/Safari, clavier, installation, actualisation de version, faible réseau, sessions expirées et parcours de paiement complet avec comptes de recette dédiés.
